# Client map analytics

The map reads the same site's member records as `/clients`. It includes every non-deleted member, including members without coordinates and members holding multiple roles. The directory and regional breakdown are paginated in the browser; neither membership nor financial totals are capped. A city is grouped with its district/state so same-named places are not merged. State abbreviations and whitespace are normalized, and an unambiguous six-digit PIN can be recovered from a pasted address. Invalid explicit PINs are flagged rather than silently replaced. Stored address fields are not rewritten by reporting.

## Financial definition

Collections are **all-time posted net plot collections for the member's currently linked plots**, not their personal ledger or receipts from every module. They come from `ledger_entries`, including negative reversals. Outstanding is calculated per sold plot as `max(sale price - net collections, 0)`; an overpaid plot does not hide another plot's balance. Cancelled/company/transferred stock does not contribute outstanding. Every plot has at most one owner: explicit buyer member ID, then most recent non-cancelled booking, then a unique normalized buyer name within the site. Ambiguous, deleted and unavailable buyers are excluded from member totals and reported as unlinked plot collections. Historical resales follow the current plot owner; this page is a portfolio report, not a historical payer ledger.

The API uses one SQL snapshot, one ledger aggregation, a name index and grouped member totals, rather than a correlated payment scan for each member. Regional aggregation and search indexing are linear in the member count, plus sorting distinct regions. Browser rendering is limited to 100 directory entries and 50 region rows per page. Leaflet remains lazy-loaded with chunked marker clustering. Shared mutation cache invalidation refreshes analytics after address, buyer, payment or approval changes.

## Locating addresses

Map reads are now able to place clients without a separate geocoding job. Address precedence is the reviewed member address, permanent address, then the newest verified KYC case in this site. KYC fallback uses only active document slots and the newest OCR result for each document. The same evidence/confidence validation as the KYC review is applied; conflicting addresses, unfinished replacement OCR and historical extractions without evidence require review. Reporting does not overwrite member/KYC fields. OCR text, document images, identity numbers and evidence are not returned in the map payload.

Indian PIN-area centroids and named localities are matched against a bundled public GeoNames reference. Distant postal-coordinate outliers are excluded during compilation. A recognized nearby town takes precedence over a postal district centroid, including historical district-name changes. State/PIN conflicts and ambiguous namesakes are rejected. A city appearing in a road name or relative-name section is not treated as the residence city. Lorem ipsum template addresses (including Hindi OCR variants found in uploaded forms) and masked sample addresses are excluded and flagged for review, never submitted to AI as addresses. Spaced Latin OCR letters are normalized for reference matching; Hindi vowel marks remain intact. Known PINs, cities and localities appear automatically as **approximate** pins; manually saved coordinates retain priority. Data sources, license and regeneration instructions are in `src/data/README.md`, and the map displays GeoNames attribution.

Verified postal corrections in `src/data/india-postal-corrections.json` take priority over outdated automatic locations, including already-saved provider coordinates and cached results. PIN 247776 uses Shamli's named locality and current district, including profiles with the historical Muzaffarnagar label or no city field. This corrects reporting without rewriting client addresses or manual pins, and survives regeneration of the GeoNames dump.

An administrator can select **Locate with AI** for remaining saved addresses when `OPENROUTER_API_KEY` is configured. This sends address text and locality fields through the existing OpenRouter completion service, using `OPENROUTER_MAP_MODEL` or `google/gemini-2.5-flash`. Names/contact/identity fields and KYC document images are excluded; relatives, recognizable long number strings and house identifiers are removed from address text. AI must supply literal locality evidence and confidence, and may repair a minor OCR spelling or recognize an alternate place name. The model cannot supply coordinates: the resulting locality must match the public reference. An unsupported or conflicting result remains unlocated.

The AI run continues in resumable 20-second batches and can be paused. Provider failures preserve the cursor for retry. Site changes/unmount abort the browser run; already-started server work may finish its current bounded batch. An application-wide PostgreSQL lock prevents overlapping workers. Successful AI locality results are cached for 180 days and misses for seven days; provider failures are not negative-cached. Address-specific cache keys contain a hash, and cache metadata contains normalized localities rather than the address. KYC/AI locations remain derived from the current address and its cache instead of overwriting profile pins. Regular profile lookups retain a snapshot comparison before saving coordinates.

The older **Locate** flow remains available without AI. Its Nominatim lookup sends city/village, district, state and PIN only, never names, contacts or full street/house addresses. Its [usage policy](https://operations.osmfoundation.org/policies/nominatim/) requires identified requests, caching and at most one request per second across the application, and permits only small one-time bulk tasks. This flow remains user-triggered and limited to one batch at a time. It is not used for automatic map reads or the continuous AI run. Set `NOMINATIM_URL` to a compatible private provider for larger needs.

## Rollout and verification

Deploy the backend and frontend changes. The new frontend opts into `dataset=members`; requests without that parameter retain the legacy `points` response, without duplicating the complete member dataset in the payload. No new migration is required beyond the existing management analytics and member KYC schema; the GeoNames reference must be shipped with the backend. The frontend must point `VITE_API_URL` at the updated API. This workspace's ignored `.env.development.local` selects the local development API. During rollout an older API continues to display saved locations; the page explains why the regional breakdown is unavailable.

- Frontend: `npm run test:client-map` and `npm run build`.
- Backend: `npm run test:client-map`.
- SQL validation: `CLIENT_MAP_DB_TEST=1 npm run test:client-map` runs synthetic table CTEs in a read-only PostgreSQL transaction. It writes no client data and makes no geocoding calls.

Tests cover duplicate names, explicit/booking buyer links, other-site exclusion, reversed/overpaid/cancelled collections, invalid/partial coordinates, multi-role filters, address parsing/invalidation, ambiguous locations, cached misses, provider outages, concurrent edits, resumable batches and 10,001-member datasets.
