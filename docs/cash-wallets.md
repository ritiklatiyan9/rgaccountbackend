# Cash Wallet

## Deployment startup

The Render entrypoint `node src/server.js` checks the installed wallet migration versions and shared runtime function definitions before running the wallet migration chain. When versions 199, 203, 204 and 207–212 are present and current, startup performs reads only and leaves the installed schema intact. This avoids replaying migration 199's source-table alterations against live reads, which can deadlock on `users` and a financial source table before the HTTP port opens. If a previous boot committed an older function before failing, startup restores the final receipt reconciliation and balance function definitions in one transaction, without rebuilding source tables or triggers, reconciling receipts, or updating accounts. `npm run ensure:wallet-startup` runs the same check independently. A missing migration runs the remaining chain in order so later shared SQL definitions and guards are restored. Errors still stop startup; readiness is never reported after a failed upgrade.

Explicit `npm run migrate` and individual migration commands retain their existing behavior for deliberate schema deployment. Changes to an already installed repeatable SQL definition should be applied through that explicit migration process, with writers stopped as described below. This startup fix does not change receipt, wallet, imprest or financial posting rules.

Cash Wallet is the single custody module at `/wallet`. It shows CASH receipt balances, original receipts, immutable custody movements and cash handover requests. The former `/loyalty-vault` addresses remain compatibility redirects/aliases. Account administrators can monitor organization holders; Sub-admins see their own custody. New cash receipts belong to the signed-in transaction maker. Historical client assignments remain available in the wallet audit and can be handed over through the existing transfer workflow.

Only Admin and Super Admin can list and inspect other holders' wallets in the selected site. Other wallet users see their own balance, transactions, movements and related transfers; another user's detail URL is blocked. The default `/holders` response contains only their own wallet. The wallet transfer picker requests `purpose=selection` to obtain holder names, with other holders' balances, pending amounts and activity timestamps hidden. Financial entry forms do not load a holder directory.

## Cash collected by

The credit transaction form's **Cash collected by** field is read-only and shows the signed-in account for every new CASH receipt, including Admin and Super Admin. Dashboard Quick Entry and all module forms use the same field. The API rejects another collector in a request body or multipart header; migration `211_locked_cash_collector` enforces the maker lock on native source inserts. Existing receipts keep their original maker and collector during edits and approvals, including historical explicit assignments. Source edits cannot reassign cash; use the wallet transfer workflow for a handover. Debit forms use the responsible user's Imprest funding.

Only incoming CASH enters the current transaction list or creates new custody. A farmer SPLIT refund contributes its incoming cash component; its bank component is excluded. Business debits and outgoing cash components never reduce a Cash Wallet balance or appear as pending wallet payments. Bank, UPI, NEFT and cheque payments create no new wallet movement. Internal bookkeeping transfers, imprest allocations, registry mappings, projected Day Book entries and duplicate personal-ledger mirrors do not mint custody.

Posting retains the application's credit-first approval policy: eligible CASH receipts post immediately, including credits awaiting review. Rejection, deletion, amount changes and recipient changes reconcile through exact compensating movements. Approval cannot credit an existing receipt twice. Every new debit must leave both the holder's organization balance and the affected site's balance nonnegative. If cash has already been handed onward, return the cash or restore funds before reducing, removing or reassigning its receipt. An unfunded correction rolls back both the source edit and its wallet movements. Historical deficits remain visible without synthetic opening funds; incoming cash can recover them.

## Expense funding

CASH expenses and other business cash debits use the responsible transaction maker's available Imprest. A farmer SPLIT payout uses Imprest only for its outgoing cash component; its bank component keeps the existing bank flow. Staff availability is posted float minus pending or waiting debit reservations. A pending or waiting expense reserves its amount; approval posts the expense once, and rejection, money-returned status or deletion releases or restores that amount. Zero or insufficient available funding prevents a new cash expense. An edit checks the replacement amount after removing that source's own existing reservation or posting, so an unchanged expense does not require funding twice.

Admins do not own a separate personal float. Their Imprest balance uses the existing `SITE_CASH` source: the site's available cash after staff floats and pending cash commitments. Pending Admin CASH expenses reserve this source, and zero or insufficient site cash prevents new expenses. Bank and other noncash expenses continue to use their existing payment account flow. Expense approval never also debits the maker's or a selected holder's Cash Wallet; cash receipts and wallet transfers remain a separate flow.

For an Admin wallet previously aligned to site cash, current cash in hand is capped at the recorded wallet balance and calculated as site cash minus outstanding staff Imprest, pending commitments, and positive current balances held in other wallets in that site. Each other holder is netted before positive balances are summed; historical deficits cannot increase Admin availability. An incoming wallet handover releases the sender's custody rather than adding the receipt to financial site cash again. This also keeps cash held by clients or retired users outside Admin's available balance. Summary, holder details, transfer funding checks and Imprest availability share this calculation. The correction is a read calculation and requires no financial data repair or database migration.

The 18 October 2026 investigation traced the overstatement to the Admin projection introduced on 16 October: it added signed Wallet transfer totals to financial site cash. On DG ASSOCIATES, a Rs 20,00,000 receipt was handed from Ravi to Kuldeep, issued back through Imprest allocation 62, and spent through farmer payment 1204. The payment and Imprest deduction 975 were posted, but the extra incoming transfer credit remained in the Admin projection. Existing tests covered outgoing handovers and Imprest spending separately; the incoming handover followed by allocation and spending was missing. The regression now covers the complete sequence and checks summary, holder details, transfer limits and other-holder custody.

Migration `217_admin_cash_custody_guard` also applies this cap to database funding checks for Admin cash expenses and Imprest. An expense edit adds back only its own existing reservation or posting before the custody cap is applied. Startup verifies the installed final function definitions, so an older repeatable migration cannot silently restore the earlier funding calculation. This migration installs functions and its schema marker; it does not rewrite financial transactions or Wallet history. Use `npm run migrate:admin-cash-custody` for an explicit upgrade and `npm run test:admin-cash-custody` for its isolated regression checks. The GitHub cash-custody workflow runs the Wallet, cash-funding and Admin custody checks on main-branch pushes and pull requests without production database credentials.

## Transfers

A pending handover does not reserve or move cash. The sender's balance stays available until acceptance. A new request cannot exceed the source holder's current balance in either the selected site or the organization, including when an administrator sends it. Only the designated signed-in recipient can accept or reject it. Acceptance locks both holder accounts, rechecks current funds and atomically debits the source holder and credits the recipient. Several requests can remain pending against the same cash; after one is accepted, another request fails acceptance if the remaining funds cannot cover it. The requesting sender can cancel a pending transfer. Rejection and cancellation do not change balances; repeated requests or decisions do not move cash twice. Administrators can hand over a known client's or retired account holder's existing custody; Sub-admins can send only their own.

Existing transaction and transfer approvals are retained. Custody entries and handovers do not create company revenue, expense, bank entries or another financial payment. Site cash and Dashboard accounting remain financial source calculations and must not be added to wallet custody totals.

## Consolidation and rollout

Migration `203_unified_cash_wallet` runs after migrations 185/186 and 199. It uses the former custody tables as the single live ledger and preserves the original `wallet_*` tables as an immutable archive. Overlapping receipt sources reconcile once. Legacy completed handovers retain their IDs, timestamps and debit/credit movements; pending requests retain their designated recipient. Noncash source balances receive compensating reversals. Migration `207_credit_wallet_imprest_debits` then makes wallet sources receipt-only and compensates previously tracked business debit deductions without rewriting the financial sources or immutable movement history. Migration `210_wallet_balance_guards` removes obsolete pending reservation caches and guards every new negative wallet delta, including receipt corrections. The compatible `reserved_balance` response field is always zero; `available_balance` equals `balance`.

The migrations do not rewrite source financial records or infer an opening balance from previously untracked historical company transactions. Existing explicitly assigned receipts and receipts already captured by the old cash wallet remain eligible; the collector lock does not rewrite them. New unassigned receipts are tracked from the permanent consolidation timestamp. Existing custody survives a holder's later role change or deactivation.

Consolidation locks the source and custody tables while copying transfer state. Afterward database guards reject writes by an obsolete API process to the archived wallet ledger, preventing a second approval or newly stranded legacy handover. Repeating migration 203 preserves its timestamp, balances and history. Apply migration 207 after older wallet migrations so the receipt-only policy and Imprest funding guards remain current, then apply site scope 208, receipt details 209 and wallet balance guards 210 in order. Earlier repeatable migrations reinstall SQL functions, so migration 210 must follow them on every startup. Migration 211 then installs the collector lock.

Deploy the backend and frontend together against the intended database. Stop all old API processes and other transaction writers before applying migrations: repeatable migrations 199, 203, 207 and 208 temporarily reinstall older SQL definitions until migrations 209 and 210 restore the final behavior. Apply the existing migration prerequisites through 208, then `209_cash_wallet_receipt_details`, `210_wallet_balance_guards` and `211_locked_cash_collector`, and restart writers only after all three complete. Normal `npm start`, the migration aggregate and direct server/development starts include these migrations in order. Both `/wallet` and the legacy `/loyalty-vault` API mount fail with `WALLET_NOT_READY` until consolidation and migrations 210/211 are ready. A frontend targeting a hosted API requires the updated backend and migrations there; local frontend changes alone cannot enforce the funding policy.

## API and verification

Migration `212_wallet_permanent_balance_guard` adds a ledger insert guard that survives older repeatable migrations replacing wallet SQL functions. Every new debit must be funded by both the holder's site ledger and organization ledger; the account row serializes competing postings. Existing historical deficits are not silently clamped.

The explicitly authorized Sunny correction uses `scripts/repair-sunny-wallet-reversal-141.mjs`. It defaults to a rollback-only preview. `--apply --output <snapshot.json>` requires a before-snapshot, validates user 2 / Mount Valley site 2 / rejected plot receipt 7646 / accepted handover, archives the complete reversal 141, and deletes only that debit while holding an exclusive ledger lock. The immutable-history trigger is restored before commit. The source receipt, rejected financial status, accepted handover and other holders are preserved. The archive prevents a later re-approval from crediting the same retained cash twice. Repeated repair calls validate the completed result and do not move money again.

Applied and independently verified on 15 October 2026: Sunny's Mount Valley wallet is `0.00`; only movements 122 and 123 remain, reversal 141 is archived, and both the permanent balance guard and immutable-history trigger are enabled. Plot payment 7646 remains rejected and the Sunny-to-Kuldeep handover remains accepted. Before/result/verified JSON snapshots are stored in `Accounts/reports/sunny-wallet-reversal-141-repair-2026-10-15*`. The isolated wallet regression run passed all 115 tests.

Run `npm run test:wallet-flow` for isolated checks of the signed-in collector lock, preserved receipt ownership during edits and approvals, cross-module cash receipts, the 20,000 expense / 15,000 cash recovery handover, unreserved transfer requests, balance guards and module descriptions in wallet history. The wallet bell uses only the selected site's own wallet movements and transfer requests, including handovers requested by an admin from that wallet. Historical source details are retained in immutable movements; current source context is read only when it still belongs to that movement's site.

Canonical endpoints are `GET /wallet`, `/holders`, `/users/:id`, `/transactions`, `/assignment`, `/history`, `/history/:id`, `/transfers`; `POST /wallet/transfers` and `/transfers/:id/accept`, `/reject`, `/cancel`. Summary retains the compatible `{ vault, pending_incoming, pending_outgoing }` response. Assignment replies include the effective holder plus `created_by` and `created_by_name` for safe edits.

The user cashbook follows a receipt / handover / running wallet layout. `/holders` and `/users/:id` expose `total_received` (recorded receipts and accepted incoming handovers, net of receipt corrections), `total_adjustments` (signed balance adjustments) and `total_handover` (outgoing handovers posted on acceptance). The compatible `total_in` includes both received cash and balance adjustments. `total_received + total_adjustments - total_handover` equals the recorded ledger balance; an aligned Admin's current cash then includes the separate cash-in-hand adjustment. A manual site-cash alignment is never labelled as cash received. These are all-date totals for the selected site, not sums of one visible page. Other holders' totals are null in a staff recipient picker. Admin and Super Admin see the all-users wallet table; staff see their own cashbook directly. The dedicated user page opens its cashbook first, keeping original cash transactions and transfer history in separate tabs.

For compatibility with an older read API, an aligned holder's Received column reads the same holder/site's all-date `/history?type=adjustment` aggregate and subtracts `totals.net` from `total_in`. It never sums the loaded page, treats missing aggregates as zero, or substitutes current cash for cumulative receipts. New API responses supply both totals directly and need no extra history read. These fields and their frontend presentation are read-only; no migration or financial posting is required.

A wallet reporting opening is separate metadata in `application_settings`, keyed by site and holder. It snapshots current cash plus the lifetime receipt/handover counters once. Thereafter Received equals opening cash plus the change in lifetime receipts, and Handed over equals the change in accepted outgoing handovers. Current cash continues to follow the existing financial/custody calculation, including expenses and Imprest. Historical postings, ledger corrections and lifetime receipt totals are preserved. `GET /wallet/reporting-openings?site_id=...` uses existing wallet visibility and site/organization scope; staff receive only their own opening. Missing opening reads must never revive the old lifetime total as a period figure.

The specifically requested Kuldeep / OM ASSOCIATES opening is prepared by `Accounts/tmp/set-kuldeep-om-reporting-opening-2026-10-25.mjs`. Default execution is rollback-only; apply requires a durable before-snapshot, writes only one settings row, checks an unchanged wallet-history fingerprint and refuses to replace an existing opening. No financial migration is required. For the local frontend while the hosted API is awaiting this read endpoint, set `VITE_WALLET_OPENING_API_URL=http://127.0.0.1:8003` in the frontend development environment. `npm run dev` starts or reuses the authenticated loopback reader automatically and validates its health before starting Vite. It has no write routes or startup migrations. It can also be run directly with `node scripts/wallet-opening-preview.mjs` from the backend; production uses the normal API once these code changes are deployed.

The local reader is blocked by default. After explicit approval for existing-session verification with the app's configured Accounts API, use `WALLET_OPENING_AUTH_MODE=upstream` for the reader (or `VITE_WALLET_OPENING_AUTH_MODE=upstream` for automatic local startup). It verifies the existing bearer token and session only at `https://rgaccountbackend.onrender.com/auth/me`, follows no redirects and rechecks organization/role access against the configured database. The UI supports the existing API's `total_balance` aggregate as a fallback: under the current receipt-only wallet rules, all outflows are paired same-site handovers, so site net receipts equal total site wallet balances.

Movement details show **Current source approval** from the live source, rather than `details.status`, which is the immutable status saved when that movement was posted. History exposes `current_source_status` and review metadata only from the same-site source. The frontend also resolves current status on opening/refresh through the existing scoped `/transactions` endpoint, using exact canonical source filters plus a source-reference search for compatibility with older APIs. It accepts a response only for the same source, holder and site; unavailable reads never revive an old pending snapshot. Accepted handovers keep their separate transfer status. Source parent IDs in history enable navigation back to the original transaction.

`/history?order=asc` returns the oldest postings first for the cashbook, while the default remains `desc` for movements and notifications. The site running sum is computed before date, source search or pagination filters, so the running wallet column includes earlier postings even on later pages. Receipt corrections remain identifiable independently of handovers. Missing new totals from an older API response display as unavailable (`—`), never as an invented zero. The user cashbook now presents **Credit** and **Debit** columns: positive movements are credits; outgoing handovers and negative receipt corrections are positive amounts in Debit. Its bounded table area scrolls entries internally, keeping the column headers and totals footer visible. Day, month, year and custom-range filters use recorded dates in IST. Both Cash wallet ledger and Cash transactions use a 27rem table area with compact rows to fit about five entries above sticky totals. Cash transactions retains day/month/year/custom-range date filters plus search and status filters. ## Connection timeouts

Wallet source reads materialize JSON and posting stages once, using native creator/date columns to filter before serializing historical rows. Concurrent summary and holder requests share only an in-flight pending-total read for the same organization and visibility. Completed totals are never cached.

Expensive wallet reads run in a read-only transaction with a local database statement timeout (`WALLET_READ_TIMEOUT_MS`, default 8000 ms, maximum 30000 ms). Timeouts roll back and release the connection; a failed rollback discards it. This does not change financial writes or migration timeouts and works with Neon's transaction pooler.

Database exhaustion returns HTTP 503 with `DATABASE_UNAVAILABLE` and `Retry-After`, including during authentication. JWT rejection and session revocation continue to return 401. The frontend preserves stored credentials when token refresh fails because of a database/network outage; it clears them only when the refresh endpoint explicitly rejects the session.

After deploying the connection-timeout fix, restart the API process to clear old requests. For an already stalled process, cancelling only the known read-only wallet CTE queries releases their connections without changing balances or financial records. The timeout fix alone does not require reapplying a wallet migration; the receipt-only wallet and Imprest funding changes require migration 207 as described above.

## Indexed wallet reads

Migration `204_cash_wallet_read_indexes` installs indexes for recent source IDs, project history and transfer inbox/holder filters, and refreshes financial table statistics once. It does not alter financial records, balances or approvals; it is included in server startup and available as `npm run migrate:wallet-read-indexes`.

Transaction reads discover eligible wallet IDs from indexed assignments, existing tracking and the consolidation cutoff before loading source rows. Materialized candidate cash rows and parameterized source primary-key lookups prevent the planner from joining complete payment tables first. Current and pending source reads include incoming cash only and skip posted receipts and rejected records before serializing source metadata, while retaining receipt approval rules, refund signs and incoming farmer split cash amounts.

At most two expensive wallet reads run concurrently by default (`WALLET_READ_CONCURRENCY`, maximum 3), leaving shared pool capacity for authentication and other modules. The admission queue is bounded and times out after five seconds. Statement timeouts and rollback cleanup still bound each admitted read. Authentication proof is reused only within the authenticated request; transfer writes revalidate their actor in the transaction. Schema readiness is cached after successful setup, never as an authorization decision.

The main page initially requests users only (`/wallet/holders?include_members=false`); known clients load when opening transfers or history filters. The header and page inbox share the same in-flight request and one visible-page poller, polling once per minute. Completed identical reads may be reused for five seconds, scoped to the signed-in user and session. Successful mutations and manual refresh invalidate cached reads, including responses that were started before the mutation. Failed reads remain retryable. Private responses are not reused across accounts or filters.
