Dashboard quick-entry transfers use a personal ledger as the debit account and an unlocked, latest-period destination ledger in the same organization and an authorized site. The destination may be in the current site or another accessible site. The selected personal ledger may become negative; the actor's cash funding account may not.

`GET /cashflow/quick-transfer-context?source_ledger_id=ID` returns `source`, `funding: {type, user_id, available_balance}`, `approval_limit`, `can_authorize`, `can_transfer`, `reason`, `date_editable`, and the current IST date as `today`. Administrators fund transfers only from their own site-scoped Cash Wallet. Sub-admins fund transfers only from their own site-scoped Imprest after pending reservations. `GET /cashflow/transfer-destinations` supplies the existing authorized destination picker.

`POST /cashflow/quick-transfers` accepts `source_ledger_id`, `destination_ledger_id`, decimal `amount`, and a UUID `idempotency_key`. Optional fields are `remarks`, `particular`, `voucher_url`, `date`, `transaction_time`, and boolean `authorize_above_limit`. Only cash is supported. The existing Cashflow transfer approval limit applies; amounts above it require an administrator's explicit confirmation. Authorization never bypasses wallet, Imprest, or site cash coverage.

The service locks site cash, ledger lineages, ledger periods, and the actor's funding account before rechecking current access and balances. A single transaction stores an immutable transfer header, equal debit/credit accounting entries, and exactly one funding debit. Retries with the same key and details return the committed transfer; changing details with that key fails. Lost/uncertain responses must retry the same request. Both accounting legs preserve the source site's transaction-date edit policy and the same date/time.

Accounting rows retain `source_module='cashflow_transfers'` so operating profit and cash reporting continue excluding internal movements. `quick_transfer_id` and `quick_transfer_leg` identify their separate direct-funding audit trail. They do not create a destination receipt in the initiating user's wallet or debit staff float again through source projection triggers.

Apply schema with `npm run migrate:quick-ledger-transfers`; normal server and local-API startup also apply migration 240 when absent, after migration 237. Reinstalling migration 237 preserves the extended quick-transfer constraint. Completed transfers, their financial legs, their Imprest funding, and ledger identities are protected against financial edits/deletion.

Run `npm run test:quick-ledger-transfers` for isolated PGlite integration coverage with the production wallet guard, wallet reconciliation, site projection, and staff Imprest reconciliation functions. Tests cover role/site authorization, own funding and reservations, same/cross-site conservation, approvals, date policy, replay, rollback, immutability, and migration reinstall compatibility. PGlite serializes complete transactions; these tests do not measure independent PostgreSQL lock timing.
