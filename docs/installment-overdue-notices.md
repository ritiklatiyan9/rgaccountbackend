# Project overdue penalty notices

The confirmed policies for OM ASSOCIATES (site 5) and Naya Baazar Unn Commercial (site 7) live in the existing `application_settings` table under `installment_overdue_notice_policy_v1`. No schema migration is needed.

- OM: 18% per year, simple daily interest on the currently unpaid overdue installment amount, using a 365-day year. Future installments are excluded. The installment detail, tracker and analytics use this project interest setting. The optional `penalty_amount` message field is an estimate on the current unpaid principal, not an accrued-interest ledger that reconstructs prior partial balances.
- Naya Baazar: a ₹50,000 shop price increase notice, once per shop when any installment becomes overdue. Only `unit_type='shop'` records qualify. Notices do not themselves rewrite the agreed sale price or post accounting transactions.

`INSTALLMENT_OVERDUE` is separate from the existing upcoming `INSTALLMENT_DUE` reminder. The existing Accountancy worker scans every minute for installments due yesterday in Asia/Kolkata, with a due date on or after the event's activation date. It re-reads canonical allocated balances before queueing and before sending. Posted cash receipts reduce the unpaid balance, although cash payment notifications stay excluded. Old tags, unapproved bookings and inactive clients cannot produce notices. Approved BOOKED, REGISTRY and UNDER CANCELLATION records are eligible.

OM is deduplicated per installment and due date. Naya Baazar's confirmed rule uses one durable outbox key per shop, across all its missed installments. Changed due dates, settled installments, disabled policies and disabled events prevent queued messages from sending. Expired/interrupted messages retain the existing worker behavior. Existing overdue portfolios are not backfilled.

Run `node scripts/prepare-overdue-templates.mjs` to review the exact confirmed policies and message bodies. With the existing sender configured, `node scripts/prepare-overdue-templates.mjs --admin-id=7 --submit --configure --enable-approved` submits missing versions, saves the two explicit project policies, and enables approved versions. If Meta approval is pending, this explicit apply request pins that exact template name and policy in `installment_overdue_requested_template_v1`. The worker applies only that requested version after approval, while its requesting administrator remains active and authorized. Changing the policy or manually saving/pausing the event cancels the request. Re-running reuses the same body/version; it never sends a customer sample or replaces a different active assignment. Meta approval alone never applies an unrequested version.

Deploy the backend with `src/services/installmentOverduePolicy.service.js` and the changes to the Accountancy WhatsApp service, event contract, installment controller and plot routes. Restart the existing backend worker with its existing `WHATSAPP_*` configuration. The local frontend still uses the hosted API; local source changes alone cannot activate its server's new event. Build/deploy the frontend to show the policy notice and its WhatsApp settings link in Plot Payments and Installment Tracker.
