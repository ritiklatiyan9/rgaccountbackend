# Request history performance report

Date: 5 November 2026. Scope: the existing request History module and the endpoints it opens. Earlier permission-module work and unrelated concurrent workspace changes are preserved.

## Result and measurement boundaries

The default UI now reads a small summary page through indexed cursor pagination, requests exact totals explicitly, and loads full receipt data only when opened. Existing callers retain the full response, offset pagination and exact totals by default. All 23 registered financial/operational history sources remain supported, including personal ledger, both commission sources, and Day Book subtypes.

The controlled HTTP benchmark meets the requested 150 ms P95 target, including its five-way concurrent workload. This is **not a measured hosted production API SLA**. The benchmark uses disposable PGlite data, loopback HTTP and fixture authentication. Native PostgreSQL plans were also measured separately, and expose material network and planning costs described below. No completed financial response cache was introduced.

The saved baseline is the implementation at the start of this optimization pass, which already contained the previous history improvements. It is not a reconstruction of the original application before all history work.

## Bottlenecks and implemented changes

| Finding | Implemented change |
| --- | --- |
| Every page could scan the archive for an exact count | UI defaults to `include_total=false`; `Count requests` requests an exact, filtered count. Existing API defaults remain unchanged. |
| Deep OFFSET pages scan progressively more keys | Signed cursor mode bounds each source by the last event time, source and native integer/UUID ID; the million-row test checks a cursor halfway through the archive. |
| The old archive index did not match the event ordering expression | Migration 236 replaces each applicable archive index with the same clock expression used by the reader, then native ID order. |
| Wide source records and audit snapshots crossed SQL/JSON boundaries | Explicit source projections; narrow candidate keys; hydrate only the selected page; summary field whitelist; full detail fetch on open. |
| Search serialized entire records, including large audit JSON | Summary searches use relevant names, amounts, categories, descriptions, references and other business fields. Legacy full-view JSON search remains compatible. |
| List rendering triggered document enrichment/signing | Summary reads skip cheque/document/party enrichment and URL signing. Full selected-record reads enrich independent parts concurrently. |
| Repeated source/schema/access probes added round trips | One site/permission bootstrap query; shared request permission map; batched relation metadata; startup schema warmup and background metadata refresh. Authorization is checked afresh. |
| Repeated identical unfinished reads could duplicate work | Scope-bound in-flight sharing only; independent consumers receive cloned rows. Completed results are discarded. |
| Unbounded reads could compete with posting writes | Existing pool reused; global history concurrency defaults to two, bounded queue and five-second driver timeout; per-user rate and concurrent-request limits. |
| Search typing rendered unchanged rows; pagination cleared the screen | 250 ms debounce, cancellation, scoped previous-page retention, skeletons and measured row-group memoization. |

The wildcard projection helper parses only trusted SQL generated by these source definitions. It expands native/derived columns, honors explicit alias overrides, and avoids duplicate `site_id`/`buyer_name` outputs. Identifier/function/nested-projection tests and live plans cover the cases found in this repository. HTTP filters never become SQL identifiers or interpolated search values.

Main implementation files:

- Backend `src/services/requestHistory.service.js`, `requestHistoryClock.js`, `requestHistoryProjection.js`, `requestHistoryCursor.js`, `requestHistoryQuery.js` and `requestHistoryWarmup.service.js`: selection, seek/index expression, projection, signed paging, bounded reads and catalog warmup.
- `src/controllers/approval.controller.js`, `src/services/operationalRequestHistory.service.js` and `src/routes/approval.routes.js`: source collection, fresh access bootstrap, summary/detail split and existing operational visibility.
- `src/middlewares/historyTransport.middleware.js`: history-only compression, private transport, limits and retryable errors.
- Frontend `src/hooks/useRequestHistory.js` and `src/components/notifications/RequestHistory.jsx`/CSS: scoped cursor state, counts, lazy receipts, filters and memoized groups. The existing Axios read adapter provides cancellation/sharing; the integrated notification lane prevents dashboard reads occupying every history transport slot.
- `src/migrations/235_request_history_indexes.js`, `236_history_keyset_order.js`, benchmark scripts, saved baselines and regression tests: reproducible rollout, rollback and evidence.

## API audit and contract

| Endpoint/path | Behavior after the change |
| --- | --- |
| `GET /approvals/history` | Server-side site, status, type, literal search and IST date filters; bounded page hydration; optional exact totals; private/no-store and negotiated gzip for responses over 1 KB. |
| Same endpoint with `source`, `record_id`, `view=full` | Targeted receipt details through the same visibility predicates and native primary-key lookup; full document/cheque/party enrichment only for that selected record. |
| `GET /approvals/:id/voucher` | Audited existing targeted lookup/site/ownership checks and private response before signing; preserved voucher regression coverage. |
| `GET /seek-permissions/:id/attachments/:index` | Audited existing visible-record lookup, per-file ownership and private/no-store signing; list summaries do not prefetch attachments. |
| Source-module navigation | Existing source links remain; no unrelated module rewrite or export API was added. |

Additive request parameters:

```text
site_id=<site>&view=summary&pagination=cursor&include_total=false&page_size=10
site_id=<site>&view=summary&pagination=cursor&after=<opaque cursor>&include_total=false
site_id=<site>&source=expense&record_id=<id>&view=full&include_total=false&page_size=1
```

The original `entries`, `total`, `page`, `page_size`, `has_more` fields remain. Cursor requests additionally return `next_cursor` and `snapshot`. An explicitly omitted count is `null`, never an estimated or stale number. A first page with no further entries can infer its exact total from the returned rows. Without the new parameters, full records, exact totals and offset behavior remain available.

Summary search intentionally omits unrelated audit/document bodies; legacy string-valued edit snapshots retain searchable identity compatibility and are compacted before returning summaries. Full detail responses preserve their original stored representation. Numeric and bigint financial values remain text at serialization boundaries to avoid JavaScript precision loss; no stored values are rewritten.

Malformed/array/object filters, invalid dates, invalid types and oversized input are rejected before execution. IDs are checked against their actual native type/range. Page size is capped at 50; the current history UI requests ten records per page.

## Database indexes, maintenance and plans

`235_request_history_indexes.js` established one partial archive index per eligible base table. `236_history_keyset_order.js` replaces those indexes in place with an ordering expression shared with `requestHistoryClock.js`:

```text
(site_id or source parent key, immutable event clock DESC NULLS LAST, id DESC)
INCLUDE (available status, timestamp, requester/reviewer fields)
WHERE lower(status) IN ('approved','accepted','received','returned','rejected','declined')
```

The native cash-flow index additionally excludes mirrored source transactions (`source_module IS NULL`). The clock preserves decision-time precedence and the database's conversion of legacy naive timestamps. A view such as `plot_status_approvals` is skipped; indexes belong to base relations. Source joins and native primary keys remain available to the planner.

Migration 236 was applied to the configured database. The final catalog audit found **22 matching indexes, all 22 valid**, rather than a second duplicate set. Replacement builds use `CREATE INDEX CONCURRENTLY`, retain the old index until the replacement is valid, then perform a short catalog-name swap and concurrent cleanup. The migration has an advisory lock, lock/build time bounds, repeat-run handling and a tested reverse migration. No history/financial rows were deleted, truncated or rewritten. `ANALYZE` refreshed statistics.

```sh
# Backend directory; target only these migrations, not unrelated pending migrations.
npm run migrate:request-history
npm run migrate:history-keyset
# Rebuild the previous archive-index ordering if rollback is required.
npm run rollback:history-keyset
```

The normal startup command now runs these targeted history migrations before starting the server. The local development reader was restarted separately; its health response identifies `request_history_version: 4`.

`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` was executed against the real generated multi-source SQL in a read-only transaction. All registered source projections planned successfully. No measured workload spilled a sort to disk. Native plans still include some sequential scans on small relations and search/count branches; indiscriminately indexing every joined text field would add write cost without matching the generated search expression.

The schema/statistics audit found autovacuum enabled. Estimated dead/live tuples included expenses 2,436/14,509, Day Book 263/1,121 and edit requests 83/226. These are planner/statistics estimates, **not measured disk bloat**. Table sizes and vacuum/analyze timestamps are saved in the audit artifact. A measured need for partitioning or a blocking table rewrite was not established; neither was performed. `pg_trgm` is available, but there is no existing synchronized cross-module search projection to index directly. No speculative trigram indexes were added.

## Cache correctness and concurrency

Redis was not added: `REDIS_URL` is not configured, direct indexed reads are fast in the controlled workload, and complete invalidation across all financial writers/instances is not presently established. A TTL page cache would weaken the explicit requirement against stale transaction history.

Only schema/relation metadata is retained. Financial reads share **unfinished work only**, keyed by actor, session/authorization scope, site, filters, view, paging and source SQL/parameters. Current grants are loaded before generating that scope. Completion removes the entry. Same-process mutation invalidation changes the generation, and explicit refresh/mutation reads use `nocache=true` to bypass earlier in-flight work. Tests verify scope isolation, no completed result reuse, independent cloned rows, invalidation and forced-refresh behavior. This is not distributed financial caching.

History SQL concurrency defaults to two (`HISTORY_QUERY_CONCURRENCY`, clamped 1–4); at most 32 reads wait, with a two-second admission timeout. A native query has a five-second driver deadline and safe retryable errors. HTTP protection allows 180 requests/minute per user/organization and at most eight active history responses per user; slots release on completion or disconnect. Limits are per process, consistent with the existing application's limiter, not a distributed quota.

## Integrity and access

Every history source retains its site/organization and requester/reviewer visibility predicates. Sub-admin history does not gain module-wide approval-decision rights. Current module grants and selected staff/wallet visibility still apply; details and attachments recheck access. History entries always set `can_decide=false`. Tests cover revoked grants, cross-site/organization denial, selected staff, personal wallets, edit ownership and existing pending-approval contracts.

Cursors are HMAC-signed, expire after 15 minutes and bind authorization and filters. Ordering retains timestamp microseconds, integer/UUID ties and NULL placement. A snapshot cap on event and creation timestamps excludes new and backdated-created arrivals during paging. Tampered cursors, changed users/grants/filters and expiry return an actionable refresh error. Use one stable `HISTORY_CURSOR_SECRET` (or the existing `JWT_ACCESS_SECRET`) across deployed instances; the random development fallback invalidates cursors on process restart.

This is timestamp-bounded pagination, not a long-running PostgreSQL transaction snapshot: changes to an existing historical row can affect later pages. Refresh starts a new sequence. No historical values, audit trails, balances, posting transactions or integrity constraints were changed.

## Remaining work and practical limits

1. Measure deployed end-to-end P50/P95/P99, including real authentication, connection pool wait and database network, with representative tenants and more samples. Desktop-to-database latency already exceeds the requested target before SQL executes. Check API/database placement and network from the deployment environment.
2. Exact totals, legacy deep OFFSET callers and arbitrary substring searches still cost more than cursor pages. Counts stay available and accurate; the UI makes that cost explicit. Native PostgreSQL planning across all sources is also material. Type filtering reduces participating sources.
3. If representative search profiling warrants it, design a maintained permission-safe business search projection and then measure a matching text/trigram index. Avoid a speculative JSON-wide GIN index.
4. Monitor autovacuum and write amplification under real churn; tune individual tables only after observing vacuum cadence and live/dead growth. Partitioning is a future measured decision.
5. Virtualization/background exports/new queue infrastructure were not justified by this ten-row UI. There is no large history export endpoint to optimize in this module. Large exports should use bounded streaming/background execution if introduced.

## Controlled HTTP benchmark

40,000 disposable rows across four sources, 20 records/page, 20 sequential reads plus 20 reads in bursts of five per scenario. Identical fixture data and search term; fresh loopback TCP connections in both runs. Before: full payload, exact count and offset. After: summary payload, count omitted, cursor seek and gzip. This comparison measures the implemented product path and explicitly includes those count/payload changes; it is not a pure SQL-only comparison. P99 with 20 samples is effectively the maximum and is not a robust tail-latency estimate.

| Scenario | Before P50 / P95 / P99 ms | After P50 / P95 / P99 ms | P95 reduction | Concurrent P95 before / after ms |
| --- | --- | --- | --- | --- |
| first_page | 39.30 / 42.00 / 42.40 | 10.51 / 12.89 / 14.08 | 69.3% | 188.66 / 56.04 |
| deep_page | 43.71 / 49.80 / 53.94 | 8.45 / 11.25 / 12.12 | 77.4% | 218.43 / 42.11 |
| literal_search | 1031.00 / 1168.78 / 1270.76 | 26.70 / 28.01 / 31.97 | 97.6% | 5298.42 / 144.10 |

First-page payload: **52,840 → 8,310 JSON bytes** (84.3% smaller); **814 bytes** on the gzip wire. Compressibility depends on actual data. The CPU-bound PGlite HTTP harness recorded 20 data queries for 20 concurrent reads in both phases, so no measured stampede-query reduction is attributed to it. Async unit tests separately prove identical in-flight SQL sharing.

Artifacts: [before](../benchmarks/history-before.json), [after](../benchmarks/history-after.json).
